# The activity trail is a module with a typed vocabulary, not a ritual repeated at every command

CONTEXT.md names the **Activity trail** as a domain concept — an append-only record of user actions that the system writes and never reads, for admins and downstream processes to mine — but the code had no module for it. `games.ts` and `auth.ts` each re-assembled the same ritual at 25 sites (`persistence.transaction` + `appendActivityTrail` + a private `persistenceError`), over an interface that took `event: string` and `payload: unknown`. Three rules that the record's usefulness depends on were held by convention alone. `web/src/trail.ts` is the module: one audited write, one error shape, and 29 declared events.

Status: accepted

## The decision

- **`write(fn)` owns the transaction; the caller keeps the ordering.** The module runs `fn` inside one transaction and hands it an `append`, so an entry and the writes it records commit or roll back together. The obvious shape — `auditedWrite(entry, writes)` — cannot express what the call sites actually do: `game-proposed` must append *after* its insert because the entry carries the id the insert returns, and `game-proposal-deleted` must append *before* its delete because the row is about to vanish. Inverting it (the module owns atomicity, the closure owns order) fits every site, including the two that write more than one entry.
- **`append(entry)` exists separately for auditing a read.** `exportGame` writes nothing but the entry; opening a transaction for one row to satisfy a uniform interface would be ceremony. Which of the two functions a command calls now states whether it had anything to be atomic with.
- **`TrailError` is `{ code: 'persistence', message }`, structurally a `GameError` *and* an `AuthError`.** Both codes unions carry `'persistence'`, so the module's own error type is assignable to both without importing either — the same one-way trick ADR-0008 used for `FilterError`. The dependency runs one way: `trail.ts` imports persistence types and nothing from `games.ts` or `auth.ts` (`ExportFormat`'s two literals are restated for that reason). Both modules keep their `persistenceError` for plain reads, which map a string and never touch the trail.
- **29 events in two families.** A game family whose every member carries `gameId`, and an account family with no such field. Three of the 29 are computed at their call sites (`game-shared`/`game-unshared` from a ternary, `player-unfollowed` from a parameter) and so are invisible to a grep for `event: '…'` — the union is now the one place the vocabulary is stated. Follow and unfollow sit in the account family despite being `games.ts` commands: following curates the find view and is about a player, not a game.
- **The two hard deletes declare `payload.gameId`.** `activity_trail.game_id` is `ON DELETE SET NULL`, so `game-proposal-deleted` and `game-deleted` would lose the column they are about. Keeping the id in the payload was a comment at two call sites; it is now a type error to forget. `game-admin-deleted` is a soft delete (`adminRemoved` is a flag, the row survives) and correctly does not carry it.
- **`userId` is required on the union, and the column stays nullable.** Every event this system records is caused by an actor. The column's nullability guards a deletion path that does not exist and, per **Account permanence** (added to CONTEXT.md with this work), is unlikely ever to exist — ranked play makes the record of who played whom permanent evidence. The schema still carries `ON DELETE CASCADE` rules that would destroy that evidence; that is `.scratch/refactoring-and-bugs/issues/02`, deliberately not touched here.
- **Persistence keeps the SQL.** ADR-0002 puts the schema and its statements in one module; `trail.ts` composes over `persistence.transaction` and `appendActivityTrail` rather than issuing its own INSERT.

## Considered options

- **`auditedWrite(entry, writes)`** — rejected: it fixes the order as entry-then-writes and allows one entry per transaction, and two call sites need neither. See above.
- **A typed `append` and nothing else** — rejected: it fixes the vocabulary and leaves the transaction ritual restated at all 25 sites, which is most of what the module exists to remove.
- **`trail.ts` owns the `activity_trail` table** — rejected: the schema would live in `db.ts` and its INSERT in a different module, against ADR-0002. It would also break the failing-persistence stub `health.test.ts` relies on.
- **A `list`/read method on the module** — rejected: there is no production reader, deliberately (CONTEXT.md: the system never uses the trail for its own logic). A production interface shaped only by tests is a hypothetical seam. The 13 raw-SQL reads in the test suite are better served by a test helper; if an admin trail view ever ships, that justifies the method and the helper shows what its interface should be.
- **Generic over the caller's error type, with a mapper argument** — rejected: it adds a parameter at every call site to express something structural compatibility already gives free.
- **A union of event *names* only, payload left `unknown`** — rejected: it is the cheaper landing and it leaves the `ON DELETE SET NULL` rule a comment, so one of the three invariants stays unenforced. Typing the payloads is the bulk of the work and it is what earns the third rule.
- **Renaming `payload.by`** — rejected. Typing the vocabulary exposed that `by` is the requester's user *id* on the four draw/take-back events but a *username* on the account events and `game-admin-deleted`: one key, two meanings. The key is stored JSON, so renaming it would split the historical record into rows that mean one thing and rows that mean another. It is typed as it actually is and documented at the union.

## Consequences

- A new command writes its entry through the module or not at all: no `persistence.transaction` or `appendActivityTrail` call remains outside `trail.ts`. A misspelt event no longer compiles.
- "A failing trail rolls the write back" is now a test (`web/test/trail.test.ts`) rather than a property nobody checked; it runs against a real database, because a stub would prove nothing about rollback. The type-level rules are tested too, with `@ts-expect-error` — `tsc` flags an unused directive, so those assertions fail loudly if the union ever stops rejecting a malformed entry.
- This is not the event log ADR-0004 rejected. Nothing is published, nothing is consumed, and commands still return domain-shaped results; the trail remains write-only evidence, which is what CONTEXT.md describes.
