# A record's per-move positions are read in one call, not one per move

The game screen's history scrubber (ticket 01) and the export command both need a stored record's position after a specific move, as TPS. Both read it through `core`'s `stateAfter(record, n)` — one call per move number. For a record with an imported PTN prefix, every single call re-parsed and re-replayed that whole prefix from scratch: O(prefix length) of work, paid again on every call, so the scrubber's loop over `M` moves cost O(M × prefix length) to render one game screen, redone on every SSE frame (ADR-0007 re-renders the game screen's regions on every change). `core`'s `positionsOf(record)` replaces `stateAfter`: it computes the imported prefix once and returns every position in the record's history in one call.

Status: accepted

## The decision

- **One call, one prefix parse, every position.** `positionsOf(record): Result<readonly string[], GameError>` returns TPS for index 0 (the empty board) through the record's total move count. `web/src/games.ts`'s scrubber loop and export's single lookup (`positionsOf(record)[throughMove]`) both call it once per request instead of once per move.
- **`replay` (private, internal to `core/src/aggregate.ts`) now keeps every intermediate state**, not just the final one — index 0 is the empty board, index *i* is the position after move *i*. `fromPtn` (its only other caller besides `positionsOf`, along with `undo`) takes `.at(-1)!` for the single state it wants; `positionsOf` uses the whole array for the imported prefix's positions. One replay loop, not two.
- **`positionsOf` and `liveState` are deliberately two different functions, not one generalized past its need.** `liveState(base, record, count)` is `loadGame`'s O(1) read of the *last* live move alone — it was, and remains, built to touch nothing before `count`, which is the entire point of ADR-0005's "reads trust the write seam" for the hot path every move and every page load goes through. `positionsOf` genuinely needs every live position, so it walks all of them — but each one through the *same trust rule* `liveState` uses for its one: a present snapshot is restored (`restoreState`, which parses and validates it), never silently replayed past. An early draft of this decision unified the two into one "walk from the start" function reused by both `loadGame` and `positionsOf`; that broke `loadGame`'s O(1) contract (touching, and validating, moves nobody asked for) and was caught by two independent tests before landing — `loadGame`'s own test ("reads the last stored position rather than replaying") and a `games.ts` test asserting an earlier corrupt snapshot doesn't block a legal move. The two functions share a trust *rule*, not an implementation.
- **`stateAfter` is deleted**, along with its own `invalid-move-number` bounds-checking (removed from core's exported `GameErrorCode` — nothing else ever produced it). A caller wanting one position now indexes into `positionsOf`'s array; there is no `n` left for core to bounds-check, since export already range-checks `throughMove` before asking.
- **One failure fails the whole result.** `positionsOf` returns `Result<readonly string[], GameError>`, not a per-index result — a single corrupt move anywhere fails the call. This matches how the scrubber already consumed `stateAfter` (aborting the whole game view on the first failure); graceful partial rendering of a corrupt record is a separate, unaddressed product question.

## Considered options

- **Trust a live move's stored snapshot verbatim, without restoring/validating it, inside `positionsOf`** — rejected: an early draft did this (skip `restoreState`, unconditionally `applyMove` to keep an internal `state` variable current, only reusing the snapshot's *string* for output). It technically satisfied "don't reparse the imported prefix repeatedly," but it silently dropped corruption detection for every live move except the last, in direct tension with ADR-0005's explicit rejection of "trusting the snapshot without the equality invariant." Caught in review before landing; `positionsOf` restores (and so validates) every snapshot it reads, exactly as `liveState` already does for the one it reads.
- **Unify `loadGame` and `positionsOf` on one "walk every live move" implementation** — rejected, see above: it breaks `loadGame`'s O(1) contract, which is load-bearing (every move and every page load calls it).
- **Return `GameState[]` instead of TPS strings** — rejected: neither call site needs the actual state object, and a live move with a stored snapshot can be used as-is (no `parseTps`/`generateTps` round trip) only if the interface deals in strings; a `GameState[]` would force every consumer through a parse the common case doesn't need.
