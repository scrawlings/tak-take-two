# A games list reads every row's to-move in one grouped query, not one load per row

The "Your games" list, the find page, and the admin list each render a "to move" column for in-play games. Every list row went through `summarise` → `loadTakGame(game)` → `storedGame` → `persistence.listMoves(game.id)` — one SQL query per row, plus a full core materialization (`loadGame`) — for a single displayed fact: which player moves next. Because these lists are SSE-streamed (the `GAMES_TOPIC` publish on every game change, ADR-0007 re-renders on each frame), the whole N+1 repeated on every frame for every open stream. The list's one needed fact already lives in the write seam: each move's row stores the resulting position as TPS (ADR-0005), and the TPS encodes whose turn it is. `web/src/persistence.ts` gains `listLastPositions(gameIds)` — one grouped query returning the last snapshot per game — and `core`'s `turnOf(position, size)` reads the next mover off a snapshot with the same parse-and-validate trust rule `restoreState` uses.

Status: accepted

## The decision

- **The persistence seam gets one grouped read: `listLastPositions(gameIds): Result<ReadonlyMap<number, string>, string>`.** One query joins each game to its last move row (by max move number) and returns that row's stored position, mirroring the batching `listLastMoveTimestamps` already did for `lastActivity`. A game with no moves, or whose last move has a null snapshot, is absent from the map — the Game module falls back to the per-record load for exactly those, preserving behavior for the imported-record-with-zero-live-moves case (ADR-0005's replay fallback).
- **`core` gains `turnOf(position, size): Result<Player, GameError>`, beside `restoreState`, sharing its trust rule.** The parse-and-size-check (`storedState`, extracted from `restoreState`) is the same in both: a snapshot that no longer parses, or whose board size disagrees with its record, is `corrupt-record` either way. `restoreState` recovers the engine's outcome on top; `turnOf` returns just `playerToMove` — the one fact a list needs. The two share a trust *rule*, not an implementation, exactly as ADR-0009's `liveState` and `positionsOf` do.
- **The Game module's `summariseAll` fetches positions once for the whole batch** and passes the map down to per-row `summarise`, which reads `turnOf(snapshot, game.boardSize)` instead of loading the record. The per-row load path survives only as the fallback for games absent from the map. This covers all three lists at once — `listMyGames`, `searchProposed` (proposed-only, so the branch never fires), and the admin `listAllGames` — because they all summarise through the same function.
- **The query count is part of the test surface.** A regression test in `web/test/games.test.ts` builds three in-play games, each with a move, spies on `persistence.listMoves` and `persistence.listLastPositions`, and asserts the list never calls `listMoves` and calls `listLastPositions` exactly once. If the per-row load ever sneaks back into the common path, the test fails — the locality the ADR promises is enforceable, not just documented.
- **Take-back needs no write-path change.** Accepting a take-back deletes the last move row (`deleteLastMove`), so the "current position" becomes the previous row's snapshot — the grouped read simply returns whatever row is last. This is why the read reuses the snapshot rather than storing a derived `to_move` fact: a stored column would have to be recomputed on that delete, which is the hand-kept-derived-fact drift ADR-0008 and ADR-0009 exist to remove.

## Considered options

- **Store a `to_move` column on `games`, written at `appendMove`/`deleteLastMove` time** — rejected. The read would be a trivial `SELECT to_move FROM games WHERE id IN (…)` with no parsing, but the fact is derived and must be kept in sync on every write path — including the take-back delete, where recomputing it requires materializing the previous state anyway, paying the very cost being avoided. It is the exact drift class ADR-0008/0009 removed from the codebase.
- **Merge `listLastMoveTimestamps` and `listLastPositions` into one query** — deferred. Both are already O(1) in query count; merging (via a window or join) would polish an optimization that is no longer the cost. The two methods mirror each other and each is trivially testable alone.
- **Have `summarise` parse the snapshot inline instead of a new core function** — rejected: it would re-implement the parse-and-size-check trust rule in the web layer, splitting corruption detection across two modules. `turnOf` keeps the rule in core, where ADR-0001 already put the rules engine and PTN/TPS, and where `restoreState` already enforces it.
