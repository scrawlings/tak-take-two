# The game screen and list views assemble in their own module, fed by the lifecycle module

The web Game module (`web/src/games.ts`, 1,748 lines at the time) had a small, clean `Games` interface — `applyGame`, `getGame`, three list methods — that was a poor map to its interior: the command rules (propose through follow, ~940 lines), a 99-line `gameView` assembly producing the 27-field `GameView`, and three list-summary assemblers (`summarise`/`summariseAll`/`sortSummaries` plus `buildBoard`/`resultTextOf`) all shared one file. "What the game screen shows, and why" could only be answered by reading the whole file — and its 155-test, command-union-riding suite. The view assembly is extracted into `web/src/game-views.ts`, fed by the lifecycle module, which keeps every read and every authorization rule.

Status: accepted

## The decision

- **A new module, `web/src/game-views.ts`, owns the view shapes and their assembly.** `GameView`, `GameSummary`, `MoveView`, `StoneView`, `BoardSquareView`, `PendingRequestView`, `PlayerRef`, and the `GameError`/`GameErrorCode` taxonomy all live there (the error type moves with `recordError`, the `(gameId, CoreGameError) → GameError` formatter both modules use). `createGameViews(deps)` returns `{ gameView, summarise, sortSummaries }`. `games.ts` re-exports the types so consumers (`views.ts`, `app.ts`, `actions.ts`) change no import lines.
- **The dependency runs one way: `games.ts` → `game-views.ts`, never back.** The view module imports from core (`positionsOf`, `formatMove`), the persistence types, `auth.ts`, and `list-query.ts` — nothing from `games.ts`. A view-shape change or a new view rule touches the view module (and its tests) alone.
- **Fed-and-decide: every read stays in the lifecycle module.** `getGame` does the visibility check (ADR-0003), name resolution, and the record+tak load, then hands the view module `{ actor, game, record, tak, nameOf }`. The three list methods share one orchestration (`summariseAll` in `games.ts`): the batch timestamp/positions/prefs reads (ADR-0010), the name cache, and per-row pre-resolution of the next mover (`toMovePlayerOf`: the batched snapshot via `turnOf`, or the rare per-record fallback for a snapshot-less imported game). The view module *decides* — every `can*` boolean, `toMove`, `viewerSeat`, `lastActivity`, `resultText` — from what it is fed; it never touches persistence or the visibility rules.
- **The straddling rules are injected, not duplicated and not moved.** Six rules are used by both commands and views: `seatOf`, `seatOfActor`, `sidesOf`, `isSelfPlay`, `deletableBy`, `joinableBy`. They keep their single statement next to the commands that enforce them, and `createGames` passes them into `createGameViews`. The factory's dependency object is the view module's interface; a test of the view module stubs it with mirroring rules.
- **The `Games` interface is unchanged.** `app.ts` (SSE streams included), `views.ts`, and the wiring tests keep calling `games.getGame`/`listMyGames`/`searchProposed`/`listAllGames`; those methods now delegate. The seam is internal — that is the point: a view change no longer threatens the command rules.
- **The export command stays command-side.** `exportGame` builds PTN/TPS text, wraps it in an ADR-0004 activity-trail write, and is a member of the `GameCommand` union. Moving it would cross the "commands authorize and persist, views shape" line for no gain.
- **View tests stop riding the command union.** `web/test/game-views.test.ts` hand-builds a `GameRecord` (plus the fed `record`/`tak`/names) and stubs the six rules; it owns the shape assertions. `games.test.ts` keeps the command and wiring tests, trimmed of duplicated shape assertions, and gains one delegation pin per read method (`getGame`, `listMyGames`, `searchProposed`, `listAllGames`) asserting the persistence-call pattern — batched, never per-row — so a refactor that moves reads into the view module fails loudly.

## Considered options

- **Let the view module own its read path (take `Persistence` directly).** Rejected: `visibleTo`/`loadVisibleGame` is used by the commands too (join, play, resign, take-back, export), so a self-reading view module would split the ADR-0003 visibility rule across two files — the exact locality loss the candidate exists to fix. Keeping reads in the lifecycle module also lets the lists batch them (ADR-0010).
- **Keep the view functions in `games.ts`, sharing the helpers.** Rejected: that is the status quo the candidate names as the problem — "what the game screen shows" requires the whole file and its command-union tests.
- **Split `GameView` and `GameSummary` assembly into two modules.** Deferred. They share nearly the whole fed seam (names, the straddling rules, the error taxonomy); splitting now would duplicate the injected dependency set or invent a third shared file, with no second consumer to justify it. If a second summary consumer appears, the seam is already drawn — the split is cheap.
- **Have `game-views.ts` import the straddling rules from `games.ts`.** Rejected: that is the reverse edge, and the moment a type import becomes a value import the two modules cycle. Injection keeps the one-directional seam and makes the view module's dependencies explicit and stubbable.
- **Move the error taxonomy to a separate file.** Rejected: the errors *are* the view vocabulary's interface (`GameError` is what `recordError` produces and what the templates' error paths read); a third file would be a home for two interfaces.
