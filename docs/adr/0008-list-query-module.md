# Games-list filters live in one schema-driven module, not three restatements

"Your games" and "Find a game" each narrow and sort through a handful of query-string filters. Before this decision, one fact per filter — its allowed values, its label, its default, whether it counts as narrowing the list away from its default view — was declared separately in `app.ts` (raw query parsing), `games.ts` (validation), and `views.ts` (labels, the "Clear" link, stream URLs). Tickets 03, 04, and 06 each added a filter by touching all three files; ticket 06 missed the third restatement (`views.ts`'s narrowed-ness check), a real bug that only code review caught. `web/src/list-query.ts` is now the one declaration: a schema per list, and the generic machinery that reads it.

Status: accepted

## The decision

- **One generic engine, not two bespoke modules.** A schema is a `Record` of filter specs, each one of four kinds — `select` (a fixed set of strings, with a `default` that is either a real value or `null` for "absent means any"), `numeric-select` (a fixed set of numbers, for `boardSize`), `toggle` (a presence-based boolean — a checkbox submits its value only when checked), `text` (trimmed free text, blank means "any"). `MY_GAMES_SCHEMA` and `FIND_GAMES_SCHEMA` are two instantiations of the same engine, not two hand-rolled parsers. Adding a filter to either list is one schema entry, not an edit to three files.
- **A filter's `default` lives in the schema, not at its call sites.** `sort`/`direction` always resolve to a real value (`'activity'`/`'desc'`), never `null` — the schema's `SelectFilter.default` field decides this, and the resolved TypeScript type reflects it (`V | null` when `default` is `null`, plain `V` otherwise), so nothing downstream needs its own `?? 'activity'`. An earlier draft of this module left that default as a call-site concern in both `games.ts` and `views.ts` — exactly the restatement this ADR exists to remove — caught by code review before landing.
- **Validation moves out of `games.ts` entirely.** `Games.listMyGames`/`searchProposed` now take an already-validated query (`Partial<MyGamesQuery>`/`Partial<FindGamesSearch>`, resolved over the schema's defaults via `resolveQuery` so a caller — mostly tests — may still supply only the fields it cares about). `app.ts` calls `list-query.ts`'s `parseQuery` once per route, before the module is ever invoked. This is a deliberate, narrow exception to ADR-0004's "routes authenticate, module authorizes": whether `sort=bogus` names a real sort key is input shaping, not a lifecycle or authorization rule, and centralizing it where the allowed values and their labels are already declared removes one of the three restatements outright. Everything ADR-0004 actually protects — who may act on a game, what a legal command is, the take-back protocol, persistence of the record — stays inside `games.ts` untouched.
- **The dependency runs one way.** `app.ts`, `games.ts`, and `views.ts` all import `list-query.ts`; it imports nothing from any of them, not even a type. A validation failure is a `FilterError` — its own type, a `{ code, message }` shape whose `code` is a hand-kept subset of `games.ts`'s `GameErrorCode` (four literals: `invalid-status`, `invalid-sort`, `invalid-board-size`, `invalid-join-type`) — which is structurally a `GameError` without `list-query.ts` importing that type. `app.ts` hands a `FilterError` straight to `statusForGameError` and to the same `pageError`/`pageAction` machinery every other module error goes through.
- **`return_to` replaces per-filter hidden fields and the `from` field.** List-mutating forms (hide, join, follow/unfollow, propose, delete) carry one opaque hidden `return_to` — the relative URL (path + query) of the list page the form was rendered on — instead of one hidden input per filter (the pattern the find page's follow form used before this) or the three-valued literal `from` field (`'games'` / `'find'` / `'game'`, for routing a refused hide or join back to the right screen). `app.ts` infers the destination from `return_to`'s own shape (a `/games/find` prefix, a bare `/games/<id>` game-view pattern, else the my-games list) instead of trusting a second, independently-set field to agree with it. `parseReturnTo` re-derives a list's query from it, falling back silently to the default view when it's missing, belongs to a different list, or no longer parses — `return_to` is never something the user typed this request, so there is nothing of theirs to hold up as wrong.
- **Not every success redirect honors `return_to`.** Hiding or deleting a row is safe to view filtered afterward (the row disappears either way). Proposing a new game is not: redirecting to an active `status=finished` filter after proposing a new `proposed` game would hide the very game just created, which reads as the proposal having silently failed. Propose's refusal path still honors `return_to` (there is no new row to hide yet); only its success redirect stays unconditionally on the unfiltered list.

## Considered options

- **Two bespoke per-list modules, each with its own parser/label/URL functions** — rejected: this would still declare "what's a valid `sort`" once per list, just relocated, and a new cross-list filter (the bots spec's `ranked`/`humans-only` tags) would cost writing the same shape twice again.
- **Keep per-filter hidden fields on every list-mutating form** — rejected: every new filter would still require touching every form on its list (hide's, join's, propose's, delete's), which is the exact repetition this ADR removes on the query-parsing side; `return_to` needs adding once and never changes when a filter is added.
- **Surface an error when `return_to` doesn't parse** — rejected: `return_to` is carried automatically, not typed by the user this request; an error would be reporting a problem to someone who submitted nothing wrong. Falling back to the default view is the same graceful degradation a direct request already gets when a filter is simply absent.
- **Keep validation inside `games.ts`, have `list-query.ts` only build labels/URLs** — rejected: this is what an earlier pass of this decision did, and it left "what's a valid `sort`" declared in `games.ts`'s own parser *and* in `list-query.ts`'s schema (for the `<option>` labels) — two of the three restatements survive instead of one. Moving validation fully into `list-query.ts` is the one change that collapses all three into a single declaration; ADR-0004's authorization boundary is preserved everywhere except this one input-shaping concern.
